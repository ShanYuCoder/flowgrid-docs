# 概要 (Overview)

本ドキュメントは、ソフトウェア開発チーム向けに書かれています：**なぜ**完全かつ構造化された成果物（Artifacts）群が必要なのか、高アジャイル環境における **SSOT（信頼できる唯一の情報源）の重要性**、納期短縮時に**開発工程がどのように省略されがちか**、そして **FlowGrid と AI がいかに連携してそれらを是正するか** を解説します。

## 3つの基本運用原則

FlowGrid は、同一のディスク SSOT 層上で**決定論的スクリプト**と **AI エージェント**を緊密に統合します：

1. **検証責務の明確な分離（量と質）：** `flowgrid audit *` および `cases:gate` は、Pure Node.js の決定論的検証により記載漏れ、スキーマエラー、未確定事項（`gaps[]`, `confirms[]`）を漏れなく検出します。一方、批判的レビュー（`/grill-bqa`, `/grill-dev`）やエンジニア審査は業務ロジックの深さと UI ↔ API ↔ テスト間の整合性を担保します。
2. **反コピペガード ＆ 共通カタログ (Anti-Copy-Paste Guard)：** `/init` スキルが共通コンポーネント候補（`CMN-UI-*`, `CMN-API-*`, `CMN-DTO-*`）を自動抽出し、`/common` による標準化を強制します。`shared/` 配下で一元管理することで、無秩序なコピペを撲滅します。
3. **高規律ワークフロー：** 未確定のギャップ（`gaps[]` + `confirms[]`）が閾値（約10件）を超えた場合、細かな質疑を一旦停止し、段階的な実行計画に移行します。大規模画面は必ず **ゾーン（Zone：ヘッダー、ツールバー、テーブル/フォーム、フッター）** に分割してコンテキストの欠落を防止します。

## 3つの導入シナリオ

| シナリオ | 特徴 | 標準運用フロー (Phase 0 ➔ Feature) |
| --- | --- | --- |
| **1. Greenfield (完全新規)** | ゼロからの新規プロダクト立ち上げ | `flowgrid setup` ➔ `/init` ➔ `/spec` ➔ `/prototype` ➔ `/api-spec` ➔ `/testcase` ➔ `/wire` |
| **2. Maintain (既存保守)** | 既存コードベースの継続的な改修・保守 | `flowgrid setup` ➔ コードを `source-code/` に配置 ➔ `/init` 構成スキャン ➔ `/trace` と `/spec` を併用して暗黙知を言語化 |
| **3. Rebase / Modernization (リプレイス)** | レガシーシステムの完全リプレイス（刷新） | 既存コードを `source-legacy/` (読取専用) に配置 ➔ `/init` で共通部品を抽出し反コピペガード起動 ➔ ゴールデンサンプルで `build-template-code` 実施 ➔ `/legacy` と `/spec` を併用 |
