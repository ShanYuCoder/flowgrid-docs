# ワークスペース構造と SSOT 成果物群 (Artifacts)

`flowgrid setup [workspace]` を実行し、`pnpm docs:dev`（または `flowgrid dev`）を起動すると、FlowGrid は標準化された **SSOT（信頼できる唯一の情報源）** アーキテクチャ骨格を生成します。

VitePress ドキュメントハブは、ローカルディスク上のこれらのディレクトリと Markdown ファイルを直接読み込み、開発チーム全体（PO/BA、フロントエンド/バックエンドエンジニア、QA、アーキテクト）が単一の統一された事実に基づいて協調作業できるようにします。

---

## ローカルディスクディレクトリの全体像

```text
my-workspace/
├── overview/               # プロダクトビジョン、事業目標、リリース計画
├── architecture/           # システム技術設計書（Arc42 標準および ERD モデル準拠）
├── surfaces/               # アプリケーション画面、機能モジュール、共通パターン、業務フロー
│   ├── common/             # [動的スコープ] 再利用可能な UX 規約、共通パターン、共有 DTO
│   ├── user-flows/         # [動的スコープ] 画面横断・サーフェス横断のエンドツーエンド業務フロー
│   └── <surface-name>/     # 具体的な業務サーフェス（admin 管理画面、portal ポータル、mobile 等）
├── .flowgrid/registries/   # UI デザインシステム、バックエンド能力、コード生成レジストリ
├── qa/                     # 業務未決事項 (Open Questions) とリスク検討用インボックス
├── source-code/            # 稼働中の本番コードリポジトリ（Git サブモジュール管理）
└── source-legacy/          # 考古学調査・リファクタリング用の旧コード（厳格に読取専用 READ-ONLY）
```

## ドキュメントハブにおける各ディレクトリの役割と責務

### 1. `overview/` — プロダクトビジョンとスコープ定義
- **内容構成：** システム全体の概要を示す `overview/index.md` およびアーキテクチャの強みを分析した `overview/strengths.md` を格納。
- **責務：**
  - 事業目標およびプロダクトが解決すべき中核課題の定義。
  - ユーザーグループの分類（*Actors & Personas*）。
  - リリースごとの機能提供範囲（Release Scope / Milestones）の策定。
- **主なステークホルダー：** プロダクトオーナー（PO）、ビジネスアナリスト（BA）、プロジェクトマネージャー。

### 2. `architecture/` — システム技術アーキテクチャ（Arc42 国際標準）
- **内容構成：** 国際標準である Arc42 アーキテクチャフレームワークに準拠した **12 の専門セクション** とデータモデル：
  - **`01-introduction/` (概要、目標、技術的ホットスポット):** システムコンテキスト、ビジネス目標、技術境界、高負荷ボトルネック等のホットスポット分析。
  - **`02-constraints/` (アーキテクチャ制約):** 不変の制約条件：必須技術スタック、ハードウェア仕様、予算、法的コンプライアンス（GDPR、ISO 等）、開発規約。
  - **`03-user-flows/` (システムコンテキスト ＆ マクロデータフロー):**
    > **`surfaces/user-flows/` との明確な違い：**
    > - **`architecture/03-user-flows/`** は**マクロシステムフロー（System Context）**を表現。サービス間、境界づけられたコンテキスト間、または外部連携におけるデータ処理サイクル（銀行突合、ERP 同期、MQ イベント駆動等）を記述。画面や UI には**一切依存しません**。
    > - **`surfaces/user-flows/`** は**対話型 UI ユーザーフロー**を表現。ボタン操作、フォーム検証、画面遷移、モーダル等、画面を横断するユーザー体験を記述。
  - **`04-solution-strategy/` (ソリューション戦略):** 基本戦略：アーキテクチャパターン選定（クリーンアーキテクチャ、DDD、マイクロサービス vs モノリス）、データ分割戦略、キャッシュ設計、Mermaid データフロー図。
  - **`05-building-blocks/` (ビルディングブロック構造 / C4 コンテナとコンポーネント):** システムの静的分解（C4 モデル）：サービス分割、内部モジュールの責務、静的依存関係。
  - **`06-runtime/` (ランタイム実行ビュー):** 主要シナリオにおける動的相互作用：シーケンス図 (*Sequence Diagram*)、起動フロー、非同期通信、排他制御。
  - **`07-deployment/` (デプロイ配置図):** 物理・仮想サーバー構成、環境定義（Dev, Staging, Prod）、コンテナ設計（K8s/Docker）、ネットワークおよび CI/CD パイプライン。
  - **`08-cross-cutting/` (横断的関心事):** 全社共通の技術標準：
    - `security.md`: 認証・認可（RBAC/ABAC）、データ暗号化、OWASP 防御基準。
    - `integration.md`: サービス間通信規約と外部 API 連携（REST, gRPC, リトライ、サーキットブレーカー）。
    - `observability.md`: ログ収集、メトリクス監視、分散トレーシング（OpenTelemetry）。
    - `conventions.md`: コーディング規約、命名規則、Git 運用ルール。
    - `configuration.md`: 環境変数とシークレット管理。
  - **`09-decisions/` (アーキテクチャ決定記録 — ADR):** 重要な技術選定の経緯（`ADR-{NNN}-{slug}.md`）を蓄積し、意思決定の背景と影響を記録。
  - **`10-quality/` (品質目標と非機能要件 — NFR):** 数値化された非機能目標：応答速度（p95/p99）、秒間リクエスト数（RPS）、稼働率（99.99%）、RTO/RPO。
  - **`11-risks/` (リスク管理と技術的負債):** 技術的リスク（*Risk Register*）と技術的負債の解消ロードマップを管理。
  - **`12-glossary/` (ユビキタス言語用語集):** 用語の定義を統一し、PO、BA、エンジニア、QA、AI の間の認識齟齬を排除。
  - **`model/` (データモデルと C4 DSL):**
    - `data-models.md`: テーブル定義、外部キー、制約条件を示す Mermaid `erDiagram`。
    - `workspace.dsl`: C4 モデルに準拠した Structurizr DSL システム構成定義。
- **責務：** チーム全体と AI エージェントが迷いなく一貫したコードを構築するための技術指針。
- **主なステークホルダー：** ソリューションアーキテクト、テックリード。

### 3. `surfaces/` — 画面サーフェス、機能、動的スコープ
- **内容構成：** 各種ユーザーインターフェース（`admin`, `portal`, `mobile`）、機能モジュール（`CMP-*`）、原子画面（`W-*`）を管理。
- **`common/` と `user-flows/` の階層的動的スコープ：**
  これら 2 つのディレクトリは**特定の単一ルートに固定されず**、再利用の範囲に応じて柔軟に階層配置されます：
  - **`common/` (スコープ別共有資産):**
    - `surfaces/common/` にある場合：**システム全体で共有**（グローバル UI 規約、共通バリデーション、確認ダイアログ）。
    - `surfaces/<surface>/common/` にある場合：**該当サーフェス内でのみ共有**（管理画面専用の共通レイアウトやフィルターバー）。
    - `<module>/common/` にある場合：**該当モジュール内でのみ共有**（注文モジュール専用のステータスバッジや専用検索器）。
    - 無秩序なコピペを撲滅し、1 箇所で再利用コンポーネントを管理。
  - **`user-flows/` (スコープ別業務フロー):**
    - 画面遷移を伴う業務フロー（`FLOW-*.md`）を管理：
      - `surfaces/user-flows/`：**サーフェスを跨ぐエンドツーエンドフロー**（例：ポータルで注文 ➔ 管理画面で承認）。
      - `surfaces/<surface>/user-flows/`：**同一サーフェス内のモジュール間連携フロー**。
      - `<module>/user-flows/`：**同一モジュール内で完結する多段ウィザード**（3 ステップ注文作成など）。
- **主なステークホルダー：** BA、フロントエンドエンジニア、バックエンドエンジニア、QA。

### 4. `.flowgrid/registries/` — 共有コンポーネント・能力レジストリ (Workspace SSOT)
- **内容構成：** 機械可読な JSON レジストリ（`design.registry.json`, `codegen.registry.json`）。アプリケーションコードを汚染せず、Workspace SSOT 内で集中管理。
- **責務：**
  - 既存の再利用可能 UI コンポーネントおよびレイアウトのカタログ化。
  - 実装済みバックエンドサービスと能力のカタログ化。
  - AI エージェントが既存資産を認識し、重複コード生成を防止して再利用を最優先するよう誘導。

### 5. `qa/` — 協調レビュー ＆ 業務未決事項インボックス
- **内容構成：** `qa/index.md` を中心に、仕様確認中の未決事項（*Open Questions*）を集約。
- **責務：**
  - エンジニアや QA が仕様確認時に発見した疑問点を記録。
  - BA や PO が `/qa-resolve` スキルを用いて正式に回答・承認。
  - 機能開発完了前にすべての疑問点が明確に解決されていることを保証。

## ワークスペースコードリポジトリ

| ディレクトリ | アクセス権 | 用途および運用ルール |
| :--- | :--- | :--- |
| **`source-code/`** | **読取 / 書込可能** | 稼働中の本番リポジトリ（フロントエンド、バックエンド）。自動生成されたコードやすべての修正はここにコミットされます。 |
| **`source-legacy/`** | **厳格に読取専用 (READ-ONLY)** | レガシーシステムの旧コード。システム刷新時の仕様調査用として参照。**直接の修正や無秩序なコピペは固く禁止されています。** |
